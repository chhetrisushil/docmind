#+OPTIONS: toc:2 num:nil

* What DocMind is

DocMind is a multi-user, local-first, RAG-based document assistant built on the Loom framework.
A signed-in user uploads documents, gets summaries and analysis, and asks questions across their
documents in a chat that cites its sources. Each user's data is isolated per tenant and encrypted
under a per-user key, so account erasure can be made final by destroying that key.

Document storage, ingestion, linked retrieval, chat and account erasure exist today (see Status); the web UI is planned.

The =ingest-document= flow (version 3.0.0) parses, chunks, embeds, analyzes, summarizes and links each
document. =/api/chats= answers questions over the user's documents with cited, streamed answers, with the model's reasoning shown and stored through Loom's ADR 0133 capture (sealed per user); version 1.0.0 of the =chat-title= flow names each chat. There is no =apps/web= yet.

* Architecture

Data flow as built:

1. =POST /api/documents= streams a multipart upload, sniffs magic bytes, applies per-user and
   per-tenant limits, and writes the bytes to the encrypted filesystem blob store under a keyed
   content address (used for dedup).
2. A row goes into the =documents= table, which is under row-level security; sensitive columns
   (=*_enc=) are encrypted with =FieldCrypto=.
3. After the upload commits, the server starts the =ingest-document= flow on Loom (ids only in the
   input and event log): parse (sandboxed child process), chunk, embed (Ollama, pgvector), analyze,
   summarize (Claude, optional), link. Deleting a document cancels every generation of the flow first.
4. =GET /api/documents= (keyset paging), =GET /api/documents/:id= and =DELETE /api/documents/:id=
   complete the API; =POST /api/documents/:id/retry= re-runs a failed document. Auth routes: =POST /api/auth/sign-up=, =/login=, =/logout=, =GET /api/me=.

5. =/api/chats= (create, list, messages, send, stream, reasoning, stop, patch, delete) runs a =doc-assistant= agent over Claude with five read-only tools; answers cite =[[chunk id]]= markers that are validated on read. See [[file:docs/design/linked-retrieval.md][linked retrieval]].
6. =DELETE /api/me= (body =password=) erases the account: it records a durable request, logs the user out
   everywhere, frees the email, answers 202 with a receipt, and a background =Eraser= stops the user's work,
   destroys the user's key (which makes every event, snapshot, sealed column and blob unreadable),
   tombstones the read models, deletes the rows, deletes the blobs and finishes. An interrupted erasure
   resumes at boot. See Operations.

Security model, in brief:
- Per-tenant isolation through Postgres row-level security. The server connects as =docmind_app=,
  which owns nothing and cannot bypass RLS; migrations run as the owner role.
- A per-user data key (DEK) is stored wrapped by a master key (KEK). Loom's event log and snapshots
  are sealed per user through =PostgresKeyStore=; blobs are enveloped per user.
- Destroying a user's key makes their events, snapshots, sealed columns and blobs unreadable (crypto-shredding); =DELETE /api/me= does that and then deletes their rows and files.
- Event paths holding sensitive fields are registered in =apps/server/app/sensitive.ts=; flow input
  carries ids only, and passwords and secrets are kept out of logs.

* Prerequisites

- Node.js >= 20 (CI uses 22).
- pnpm 9.14.4 (pinned in =packageManager=).
- PostgreSQL 16 (CI and =docker-compose.yml= use the =pgvector/pgvector:pg16= image). pgvector is not
  needed until M3.
- A sibling Loom checkout at =../loom=, built with =pnpm build=. =package.json= overrides every
  =@loom/*= dependency with =link:../loom/...=, so install fails without it.
- Optional: Docker, for the compose services (Postgres, and Ollama on port 11434 for embeddings in M3).

* Getting started

Clone DocMind beside Loom:

#+begin_src text
workspace/
  loom/      (run: pnpm install && pnpm build)
  docmind/
#+end_src

#+begin_src bash
cd docmind
pnpm install
pnpm build
docker compose up -d            # Postgres (+ Ollama); binds to 127.0.0.1
cp .env.example .env            # then edit; .env is git-ignored
set -a; . ./.env; set +a
pnpm --filter @docmind/server db:migrate
pnpm --filter @docmind/server start
#+end_src

* Development

Run from the repository root:

| Script                 | What it does                                      |
|------------------------+---------------------------------------------------|
| =pnpm build=           | =turbo run build= (tsc per package)               |
| =pnpm test=            | =turbo run test= (vitest per package)             |
| =pnpm typecheck=       | =turbo run typecheck=                             |
| =pnpm typecheck:tests= | =turbo run typecheck:tests=                       |
| =pnpm lint=            | =biome check .= (=pnpm lint:fix= writes fixes)    |

Postgres-backed suites run only when =DOCMIND_TEST_PG_URL= is set; otherwise they skip. The role
needs =CREATE DATABASE=, because each suite creates and drops its own database. Migrations are a
Turbo test input, so changing one reruns tests.

CI (=.github/workflows/ci.yml=) checks out Loom next to this repo, builds it, then builds,
typechecks, lints and tests DocMind. Draft pull requests skip CI. The design spec asks for pull
requests of at most 200 changed lines and 10 files, opened as drafts.

* Operations

- [[file:docs/operations/rotate-kek.md][Rotating the master key (KEK)]]: re-wraps stored data keys with
  =pnpm --filter @docmind/server keys:rotate=.

- [[file:docs/operations/backfill.md][Backfilling ingestion for old documents]]:
  =pnpm --filter @docmind/server backfill:ingest -- --days N=. *Stop the server first*: the backfill
  runs its own flow engine, and only one engine may drive a database. Exit codes: 0 done, 1 failure,
  2 bad arguments, 3 incomplete (run again).
- Retry: =POST /api/documents/:id/retry= restarts a failed document from the step that failed; steps
  skip work an earlier attempt finished. A fresh parse clears the document's chunks and summary. The
  parsed text of a failed document stays sealed until a retry or a delete.
- Upgrading from flow version 2.3.0: executions still running under it are given up
  (=ingest-flow-mismatch=); the user can retry them.
- Chat: without =ANTHROPIC_API_KEY= creating a chat and sending a message answer 503 =chat_unavailable=; the rest works. Rotating the envelope key: set the old one as =DOCMIND_CHAT_ENVELOPE_KEY_PREVIOUS=, the new one as =DOCMIND_CHAT_ENVELOPE_KEY=, restart, and remove the previous key after an hour. The first boot after this release re-folds the ingest-status read model once, because sealing the chat and reasoning event paths changes its fold version. pgvector 0.8.0 or later is required (the server refuses to start below it). If the chat-activity model cannot start, the server logs it and lists chats by creation time.
- Chat cost: one chat turn is a few model calls (one per tool round); titles use the small model once per chat. The chat flow has no turn deadline: the provider's 180 s request timeout bounds each attempt, and a tool times out after 30 s.
- Erasure: =DELETE /api/me= with ={"password": "..."}= answers 202 and erases in the background (409
  =erasure_in_progress= if one is already recorded). Watch it with =SELECT state, steps, attempts FROM
  erasure_requests= (as the owner role): =steps= lists the steps done, in order (=stop=, =shred=,
  =readModels=, =rows=, =blobs=, =key=, =done=), and =state= is =done= at the end. A failing step is retried
  without limit, with a backoff of 1 s to 60 s; the log shows only the step name, the error class and the
  attempt. A shred that waits on a running chat turn logs =ErasureParkedError= until the turn ends (a stop
  has been sent; normally seconds). Erasure resumes by itself at the next boot, and the server rescans every
  5 minutes. What stays afterwards is listed in the spec (§4.4, trade-off 7): ids, event types, tombstones
  and the audit row, none of it content.
- Erasure receipt: the 202 body carries a =receipt=; =GET /api/erasure/<receipt>= (no login) answers 200
  ={"state": "pending"}= or ={"state": "done"}=, and 404 for anything else. Only the receipt's sha256 is
  stored. The account's email is released at the 202, so the same address can sign up again at once.
- Erasure runbook:
  - A step that keeps failing logs =erasure stuck <step> <ErrorClass> attempts=<n>= after 10 attempts and
    again every 10 (no ids); search the log for =erasure stuck=. Read the class: a database that is down or a
    migration that narrowed a grant shows up on =rows= or =key=; =ErasureParkedError= on =shred= is a chat
    turn that will not park. Fix the cause; the next retry (at most 60 s later) continues from that step.
  - A =DELETE /api/me= that answers 500 may have committed: the erasure can be accepted with no receipt
    reaching the user. Check =erasure_requests= by user id. If the row exists, the erasure runs; the user
    cannot log in (the email was replaced).
  - The eraser runs at most two erasures at a time. An erasure that is waiting out a retry delay holds neither
    a slot nor its lock, so stuck erasures do not hold up the others; the stuck lines tell which are stuck.
  - The lists behind the boot resume, the rescan and the post-boot re-tombstoning (=pending()=, =erased()=) page
    through =erasure_requests= by user id, 500 rows per call, so no request is skipped. The boot resume and each rescan read every request this way; each hold attempt's =get()=
    scans pages up to the user's id.
  - Log compaction: DocMind turns none on. =compactionExempt= covers ingest and chat executions, and a
    tripwire test (=app/retention.test.ts=) fails if either is dropped from it, or if any non-test source under
    =apps/server= calls =compact=. It does not prove that a new flow is safe to compact: when adding a
    suspendable flow or retention (M7), extend =compactionExempt=. Loom's erasure coordinator documents one
    residual for a log compacted through its tip behind a sealed checkpoint; see =config.ts=.
- Backups: keep database backups (Postgres dumps, WAL archives, the key-store rows) for at most 30 days.
  An erasure cannot reach a copy that already exists, so the copy's life is the erasure's last step. After
  restoring a backup, re-run erasures made since it was taken: insert their ids into =erasure_requests=
  as =pending= (the audit rows of the live database are the list) and start the server. A backup of the
  key store that outlives the 30 days defeats erasure for everyone in it; delete it on the same schedule.
  The blob directory is encrypted per user and needs the same schedule.
- Cost: a summary makes one Claude request per 24,000 characters of text (at most 400,000 characters:
  at least about 17 map requests, up to about twice that when sections are just over 12,000
  characters, since whole sections are packed) plus one reduce request. Vision reads at most 12 text-less pages per PDF, 4 per request
  (PDFs over 100 pages or 22 MiB raw are refused for vision); images are limited to 5 MiB of base64
  and 8000 px a side. Per-tenant token budgets come in M7.
- A backlog of interrupted summaries is re-driven one step at a time on recovery (up to 10 minutes
  each), which can delay recovery of other executions after a restart.

The backup and restore drill (restore into an empty database, verify, re-run erasures) is M7 work; the rules above are the ones that hold today.

** Deployment notes (v1)

- HTTP limits: request headers must arrive within 20 s, 60 s per route except upload and SSE (upload
  bodies are not cut off at a fixed time), keep-alive 5 s. A refused cross-origin write is logged
  with the matched route pattern, at most once per 60 s per route.

- One server (one flow engine) per database. Recovery after a restart assumes no second process is
  driving the same executions; running several nodes needs fencing work first.
- Cap host memory (a container or cgroup limit, or systemd =MemoryMax=). The parser's
  =--max-old-space-size= bounds only the V8 heap, not Buffers or other native memory.
- Run the server so that stopping it kills its whole process group: systemd =KillMode=control-group=
  (the default), or a container. Parser children are killed on a clean shutdown, but after a crash
  or =SIGKILL= of the server only the group kill reliably ends them.
- A reverse proxy must forward =Host= unchanged, or browser writes without Fetch Metadata are
  refused with 403. See the comments in [[file:.env.example][.env.example]] (=DOCMIND_COOKIE_SECURE=,
  =DOCMIND_TRUST_PROXY=).
- The =vector= (pgvector) extension must be created by a superuser or the DBA before migrating:
  the migration runner refuses to continue without it. After a pgvector upgrade, the app role needs
  EXECUTE on the new extension functions again, so ship a grant migration with the upgrade.
- Applied migration files are checksummed (SHA-256, BOM and CRLF ignored). =db:migrate= and the server
  start refuse a file that changed after it was applied. The first run against a database from
  before checksums records the files as they are now (trust on first use). Never edit an applied
  file: add a new migration. To accept a legitimate edit, update that row's =checksum= in
  =schema_migrations= by hand.

** Known limits

- PDFs in CJK scripts that need predefined CMaps extract as empty text and are sent to vision.
- The word segmentation in =analyze= is synchronous.
- Chats run in one process; a turn in progress when the process dies is run again after restart.
- A chat left on an old flow version is logged and left at recovery; a flow version bump needs the previous version registered beside the new one.
- A title is skipped (and not retried) if the model is down or the first question is not recorded in time.
- Search filtered by documents is exact; unfiltered search is approximate (HNSW with iterative scans). Chunks are searchable once embedded, whatever the document's status.
- Erasure (M5) must also cover =chat_sessions=, =chat_turn_items=, =chat_reasoning_texts= and the =chat-activity= read-model rows, plus: the =ingest-status= and =chat-activity= read-model rows of chat and chat-title executions (their key and scope may be NULL, so purge by execution id prefix =u_<user>=), the Loom timers rows, the chat-title executions, and the conversation streams (destroying the user's key covers their content).
- Documents that reached =ready= before flow 3.0.0 never get stats, summary, entities or links.
  Re-upload them; a re-ingest tool is planned for M7. There is no production data yet.
- Parse retries use =LLM_RETRY= for every format (a crash is retried as patiently as a Claude outage).
- A summarize attempt can hold one of the process's ingest slots for up to 10 minutes.
